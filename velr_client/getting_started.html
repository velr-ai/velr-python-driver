velr_client.getting_started

Velr Python server client

velr-client is a synchronous Python client for querying and administering an existing Velr Server. Use the separate velr package for an in-process database.

Requirements and installation

Use Python 3.12 or later with standard-library socket and TLS support. The client requires a reachable Velr Server native endpoint, normally port 7777, and an identity authorized for the databases and operations you use. Secured connections require TLS 1.3. The client has no third-party runtime dependencies and does not start or configure a server.

Quick start

With an existing local server listening on 127.0.0.1:7777:

from velr_client import VelrClient

with VelrClient.connect("127.0.0.1", 7777) as client:
    client.run(
        "MERGE (:Person {name:$name})", params={"name": "Alice"}
    ).collect()
    result = client.run(
        "MATCH (p:Person {name:$name}) RETURN p.name AS name",
        params={"name": "Alice"},
    )
    print(result.columns)    # ['name']
    print(result.collect())  # [['Alice']]

The initial database is default. For a secured endpoint, use connect_tls() with the required trust and authentication options; see the connection guide. MERGE creates the matching person when absent. The first result is consumed before starting the read; application values are supplied separately from Cypher.

Secure connections

Use a verified TLS connection and load the bearer token from your secret provider or environment. connect_cluster() also enables session recovery:

import os
from velr_client import VelrClient

with VelrClient.connect_cluster(
    "db.example.com",
    7777,
    ca_file="/run/secrets/velr-ca.pem",
    server_hostname="db.example.com",
    token=os.environ["VELR_TOKEN"],
    timeout=5.0,
) as client:
    print(client.status()["server_version"])

Replace the hostname and CA path with your endpoint and trust configuration. connect_tls() is a direct TLS connection without automatic session recovery; it uses system trust roots when ca_file is omitted. For a supplied ssl.SSLContext, configure certificate/hostname verification, TLS 1.3, and ALPN velr-native/1 yourself. The context is used unchanged.

Connection timeout is a socket timeout in seconds, including later blocking socket operations. The query deadline is set separately on run(). Cluster factories expose reconnect rounds, backoff, and gateway refresh options; ordinary commands interrupted by a lost connection are never automatically replayed.

Queries and results

run() returns a ClientResult. columns gives column names; collect() returns all remaining rows as lists of Python values. Use pull(batch_size) to consume large results incrementally, or discard() to finish without retaining unread rows. Retrieved rows are owned Python values.

Finish or discard each result before another command, selecting a different database, or ending a transaction. A result is not an iterator or context manager. Closing a client closes its connection and invalidates its handles; use with or call close() explicitly. Closing is safe to repeat.

Reading in batches

For results too large to collect, pull a bounded batch at a time. Discard any remaining rows if application processing stops early:

from velr_client import VelrClient

with VelrClient.connect() as client:
    result = client.run(
        "UNWIND $names AS name RETURN name ORDER BY name",
        params={"names": ["Ada", "Grace"]},
    )
    try:
        while batch := result.pull(100):
            for row in batch:
                print(row[0])  # Ada, then Grace
    finally:
        result.discard()

pull(limit) requires a positive batch size and returns [] after exhaustion. collect() consumes all remaining rows, rather than restarting the result. row_count is the initial server-reported count and can be zero when the total is unknown. Discarding a result does not undo writes.

Parameters and query controls

Query text uses $name; keys in params omit $. Values may be None, booleans, signed 64-bit integers, finite floats, strings, lists, and dictionaries with string keys. Convert objects such as datetime and bytes before binding them. Strings are data and are never interpolated as query text. Result cells are JSON-decoded Python values, with rows in column order.

max_rows=None leaves the result uncapped; zero requests column metadata without rows. This limits returned rows, not the number of graph objects a write changes. timeout is a finite, nonnegative number of seconds covering execution and result fetching. Pass a CancellationToken to request cancellation from another thread. A canceled token remains canceled; create a fresh token for independent work. See deadlines and cancellation.

from velr_client import CancellationToken, VelrClient, VelrClientError

stop = CancellationToken()
with VelrClient.connect() as client:
    try:
        result = client.run(
            "UNWIND [1, 2, 3] AS n RETURN n",
            max_rows=2,
            timeout=5.0,
            cancellation=stop,
        )
        assert result.collect() == [[1], [2]]
    except VelrClientError as error:
        if error.code not in {"query.cancelled", "query.deadline_exceeded"}:
            raise
        print(error.code)

Call stop.cancel() from your stop handler or another thread. A zero query timeout expires immediately. A stopped replicated write with an unconfirmed outcome reports query.outcome_unknown; do not assume it rolled back.

Transactions

Explicit interactive transactions require an RF=1 database. Replicated databases use supported autocommit writes. Finish the current result before commit(tx) or rollback(tx):

from velr_client import VelrClient

with VelrClient.connect() as client:
    tx = client.begin()
    try:
        client.run("CREATE (:Person {name: $name})", params={"name": "Alice"}).collect()
    except Exception:
        client.rollback(tx)
        raise
    else:
        client.commit(tx)

Connection loss does not restore a transaction. A lost commit response leaves its outcome unknown. See transaction restrictions.

Errors and concurrency

Catch VelrClientError around both execution and result consumption. Its code identifies the server/client failure. report aliases the existing message: the full original diagnostic without a code prefix. str(error) retains its existing code-prefixed presentation. With a server providing structured diagnostics, catch QueryError or a specific subclass such as ParameterError, ConstraintError, or CypherTypeError. Inspect stable category and detail fields instead of matching diagnostic wording. explanation is the separate human-readable summary; optional phase, hint, and position supply context. A known position is a public ErrorPosition named tuple, imported from velr_client, with one-based integer .line and .column fields. Columns count display cells, so wide and combining characters can differ from editor offsets. Tuple indexing, unpacking, and equality remain supported; unknown positions and other unavailable optional metadata are None. See the error-handling examples.

DatabaseBusyError exposes retryable and optional SQLite error codes, without guaranteeing that replaying a write or transaction is safe. ReadOnlyError, MigrationRequiredError, and HandleStateError identify their corrective action. QueryCancelled and DeadlineExceeded retain codes query.cancelled and query.deadline_exceeded; DeadlineExceeded also inherits TimeoutError. Older servers retain ordinary VelrClientError failures and existing codes when structured information is unavailable. Socket/TLS setup can raise OSError or ssl.SSLError, and unsupported JSON serialization can raise TypeError.

A lost ordinary write response has an unknown outcome. Use run_idempotent() from the first attempt for supported replicated writes that need safe retries, keeping the operation ID and inputs unchanged. Read the retry contract before retrying a write. OutcomeUnknownError has retryable=False; its original transport exception, when present, remains available as __cause__. ProtocolError identifies malformed or unexpected peer frames.

Clients, results, transactions, and database handles must be used serially. Open separate clients for concurrent work. This client provides no async API, connection pool, or automatic transaction retry.

For an ordinary query error, correct the query or inputs using the diagnostic message. For client.connection_lost, the interrupted operation's outcome can be unknown even if session recovery succeeds. Recovery restores the identity and selected database, but does not restore a pending result or transaction. reconnect() makes another bounded recovery attempt for a cluster client; direct connections require a new client.

Indexed SEARCH queries

Use client.run(query, params=...) or db.run(query, params=...) for the same SEARCH syntax supported by the server runtime. After creating a fulltext index:

MATCH (p:Paper)
SEARCH p IN (FULLTEXT INDEX paperText FOR $text LIMIT 10)
SCORE AS score
RETURN p.title AS title, score ORDER BY score DESC

For an existing vector index, bind a numeric vector of its declared dimensions:

MATCH (c:Chunk)
SEARCH c IN (VECTOR INDEX chunkEmbedding FOR $vector LIMIT 5)
SCORE AS score
RETURN c.text AS text, score ORDER BY score DESC

LIMIT inside the search is required. Fulltext additionally supports WITH ANALYZER and SKIP / OFFSET. Vector inner filters use properties declared with WITH [...] on the index and apply before nearest-neighbor selection; an outer WHERE filters the selected candidates afterward. Cosine SEARCH and vector procedure scores use (1 + cosine) / 2 in 0..1. Convert an older raw cosine procedure threshold t to (1 + t) / 2. For Euclidean/L2, SEARCH returns 1 / (1 + squaredDistance) and the procedures return -squaredDistance. Dot-product scores are unbounded. See the SEARCH reference for complete syntax and restrictions. The server runtime determines the available clauses and scores.

Use SHOW INDEXES to inspect index names and families. CALL db.labels(), CALL db.relationshipTypes(), and CALL db.propertyKeys() list graph catalog names through the normal query API.

Named databases

Select an existing ready database with a RemoteDatabase handle:

from velr_client import VelrClient

with VelrClient.connect() as client:
    db = client.database("customer-a")
    result = db.run("RETURN $value AS value", params={"value": 42})
    assert result.collect() == [[42]]
    print(db.status()["lifecycle"])

The database must exist and be accessible to your identity. A handle uses the client's connection and selects its database before querying; handles do not provide independent concurrent sessions. Finish results and transactions before switching between them. route_database(name) selects a database for subsequent client calls; route_default_database() selects default.

Read consistency

The default consistency="leader" reads from the current leader. On replicated databases, use "read_your_writes" to wait for earlier operations made through the same selected client database:

from velr_client import VelrClient

with VelrClient.connect() as client:
    client.run("CREATE (:Person {name:'Alice'})").collect()
    result = client.run(
        "MATCH (p:Person {name:'Alice'}) RETURN p.name AS name",
        consistency="read_your_writes",
    )
    print(result.collect())
    token = client.causal_token

Pass a saved token as causal_token=token when handing a dependency to another connection. Tokens belong to one database; selecting a database clears the client's remembered token. "stale" allows an immediately available local replica, "local" reads locally committed state, and "linearizable" confirms current authority before reading. Choose the consistency your application needs.

Retrying replicated writes

Create an operation ID once for each logical write and use it on the first attempt. The target must be a Raft-managed database supporting idempotent writes:

from velr_client import VelrClient, VelrClientError

operation_id = "audit-event:request-1042"
with VelrClient.connect_cluster("127.0.0.1", 7777) as client:
    for attempt in range(3):
        try:
            result = client.run_idempotent(
                "CREATE (:AuditEvent {id:$id}) RETURN $id AS id",
                operation_id,
                params={"id": "request-1042"},
            )
            rows = result.collect()
            break
        except VelrClientError as error:
            if error.code != "client.connection_lost" or attempt == 2:
                raise
    assert rows == [["request-1042"]]
    print(result.replayed)

This plaintext endpoint is for local development; use the TLS configuration above for a secured cluster. Keep the operation ID, Cypher, parameters, and result limit identical on retries. Reusing an ID with different inputs is rejected. replayed indicates that the returned result came from an earlier successful attempt. Reads and explicit transactions are rejected by this API.

An ordinary write cannot be made retry-safe after losing its response. When retries must survive process failure, persist the ID and immutable inputs before the first attempt and retain the pending work until a successful result is durably recorded. See the retry guide for a durable workflow and backoff strategy.

Status and administration

client.status() returns server version, uptime, metrics, and optional feature sections. db.status() returns the selected database's lifecycle information. Use the appropriate status when checking availability or waiting for a change.

Operation Methods
Inspect databases list_databases(), database_status(name)
Create a database create_database(name, request_id=...)
Change database replication alter_database_replication_factor(name, replication_factor, request_id=...)
Inspect the cluster cluster_status(), list_nodes()
Manage node lifecycle join_node(), activate_node(), drain_node(), declare_node_lost(), remove_node()
Apply cluster policy set_cluster_policy(), rebalance_cluster()

These operations require administrative permissions. Supply a stable request_id when a requested change must be retried across connections or process restarts. An accepted lifecycle change may still be in progress: poll database_status() until it is ready before using a newly created database, with an application deadline and handling for failed state. The guide covers the returned records, required fields, and lifecycle transitions.

Compatibility and maintenance

The native connection limits each request or response frame to 16 MiB. The stored-result limit for idempotent writes is separately 16 MiB. Use manageable parameter payloads and pull batches for large results. Database and node administration can change persistent server state; consult the method's permissions, confirmation, and retry rules before invoking it.

delete_database() requires retained-file deletion with retain_data=True. Destructive online file deletion is rejected. Drain and inspect a node before requesting removal; changing a lifecycle state is not proof that evacuation has finished. Administrative commands are not automatically replayed by the client.
